- A non-object argument is treated as an empty object, so every required field is missing and the call fails.
- Each method reads its input fields inside a try/catch. Any unexpected exception returns { ok: false } and is treated as a failed call.
- Expiry processing runs only when the date is a valid date string. If the date is invalid, no expiry runs.
- For dated methods, expiry runs before the IDs and amount are checked, so it runs even when those checks fail.
- A failed call returns only { ok: false } with no reason field.
- Dates are validated with a regex and a round-trip check through the JS Date type, using the proleptic Gregorian calendar. Year 0000 is accepted.
- Internally, dates are stored as UTC epoch day numbers and converted back to YYYY-MM-DD strings for output.
- Only strings are accepted as IDs. Numbers and other types are rejected even when they look like IDs.
- Book and member IDs are stored as separate Map keys, so a book and a member may share the same ID string.
- Loans are listed in the order they started. A renewal does not change that order.
- Holds are listed in the order they were placed. Removing a hold, whether by borrowing, expiry, or the member's own action, removes it from that order.
- A member's loan on a book blocks that member from placing a hold on the same book. Being in a book's hold line blocks a second hold on that book.
- A book that is set aside for a member can be borrowed only by that member, even if the member has overdue loans or owes at least BLOCK_THRESHOLD. Such a borrow fails under the §5.5 rules.
- When the reserved member borrows a set-aside book, the book's readyUntil is cleared and the rest of the hold line keeps its order.
- When a book is set aside, readyUntil is stored and returned as a date. When the book is not set aside for the member, readyUntil in getMember is null.
- A hold on a book that is set aside for another member is allowed even when the requesting member owes BLOCK_THRESHOLD or more, because §5.8 permits holds regardless of balance.
- A renewal's new due date is D + LOAN_DAYS. The spec's "never earlier" guarantee holds because D is never before the previous action's date.
- The fine on return is computed with the spec formula. Because returns are never before the due date in practice, the late count is never negative in normal use, and Math.max(0, …) covers the rest.
- payFine validates the date and runs expiry before validating memberId and amount, following the §5.3 order.
- getMember returns fresh arrays and objects for loans and holds, so callers cannot change library state through them.
